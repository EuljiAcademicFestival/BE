# 조회 쿼리 최적화

## 문제와 변경

기존 `GuestbookQueryAdapter`는 상세 1명, 방명록 목록, 상위 순위를 조회할 때마다
전체 방명록에 `RANK()`를 적용했다. 개발 DB 203행의 실행 계획에서 전체 스캔,
203행 정렬과 CTE 구체화를 확인했다. 목록은 이후 다시 정렬하고 LIMIT를 적용했다.

순위는 1~3위만 노출하므로 전체 회원의 순위 계산이 필요하지 않다.

- 기존 인기순 인덱스에서 좋아요 수가 가장 높은 **3행**을 먼저 읽는다.
- 그 3행에 경쟁 순위 `RANK()`를 적용하고 같은 점수를 하나로 묶는다.
- 점수를 원본 방명록과 연결해 해당 점수의 모든 동점자를 포함한다.
- 상세는 대상 회원을 PK로 조회하고 작은 점수·순위 테이블을 연결한다.
- 목록은 인기순/최신순 인덱스와 커서 조건으로 페이지를 먼저 선택하고,
  그 페이지에만 회원 정보·메시지·순위·개인별 좋아요 여부를 붙인다.
- 최신순 페이지 선택에서는 인덱스에 없는 `like_count`를 읽지 않아
  기존 `idx_guestbook_latest`의 커버링 인덱스 스캔을 활용한다.

상위 3행은 최종 응답 3명 제한을 의미하지 않는다. 순위가 3 이하인 점수는 반드시
상위 3행에 등장한다. 예를 들어 점수 `10,10,9,9,9`는 `1,1,3,3,3` 모두 반환하며,
동점 1위가 100명이면 100명 모두 반환한다. 3위 밖의 순위는 기존과 같이 null이다.

API 형식, 공동 순위 규칙, 정렬 키, 커서 형식, 트랜잭션과 DB 스키마를 유지했다.
새 인덱스와 캐시는 추가하지 않았다. 캐릭터 이름표 쿼리는 기존대로 유지했다.

## 검증

- `EXPLAIN ANALYZE`는 개발 DB 3306의 **일반 SELECT만**, 읽기 전용 트랜잭션에서 실행했다.
  개발 데이터에 INSERT/UPDATE/DELETE 또는 DDL을 실행하지 않았다.
- 별도 MySQL 13307의 `eulji_festival_test`에서 전체 테스트 **29개 통과**.
  실패·오류·건너뜀 0개, `bootJar` 빌드 성공.
- 회귀 테스트는 전체 행에 RANK를 적용하는 독립적인 기준 쿼리와 결과를 비교한다.
  빈 결과, 1~2명, 전원 동점, 1위 동점으로 2·3위가 없는 경우, 3위 다수 동점,
  120명의 고정 난수 점수와 서로 같거나 다른 작성 시각을 포함한다.
- 상세·상위 순위와 인기순/최신순의 페이지 크기 1·3·21·100에 대해 모든 페이지를 비교했다.
  개인별 `likedByMe`와 누락·중복 없는 커서 이동도 검증했다.
- 검증 후 임시 MySQL 13307을 종료했다. 별도 백엔드는 실행하지 않았고
  사용자의 8080 서버와 개발 MySQL 3306은 종료하지 않았다.

## SQL 단독 비교

2026-11-15, MySQL 8.0.46의 개발 DB 203행에서 동일한 읽기 스냅샷으로 비교했다.
각 쿼리 4회 워밍업 후 20회 측정했으며 수정 전후 실행 순서를 번갈아 배치했다.
아래 값은 `EXPLAIN ANALYZE` 최상위 실행기의 완료 시간 중앙값이다.
네트워크, 인증 필터, JSON 직렬화 및 동시 요청 대기를 포함한 HTTP 응답 시간이 아니다.

| 쿼리 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 상세 1명 | 0.13900ms | 0.00631ms |
| 상위 순위 | 0.13550ms | 0.01725ms |
| 인기순 첫 21행 | 0.15700ms | 0.06095ms |
| 최신순 첫 21행 | 0.15100ms | 0.05825ms |

순위 계산의 입력은 203행에서 최대 3행으로 줄었고,
첫 페이지 후보 선택은 기존 정렬 인덱스에서 21행을 읽는 실행 계획을 확인했다.
최종 페이지 순서를 보장하기 위한 작은 정렬은 남아 있다.
동점 상위 회원 수가 많으면 그 회원들은 모두 반환해야 하므로 응답 작업량도 증가한다.

API 속도 개선율로 해석하지 않는다. 기존 서버의 최적화 전 200 VU 결과는

## 5. 200명 혼합 부하 재검증 조건

이번 대표 결과는 **쿼리 최적화 후 실제 8080 개발 서버**의 측정이다. 이전 대표 결과였던 데드락 수정 후·쿼리 최적화 전의 8080 실행과 비교한다.

| 날짜 및 시간 | 2026-11-15 03:19:19 ~ 03:27:32 KST |
| 계정 준비 완료 | 03:20:31 KST |
| 앱 / DB | 127.0.0.1:8080 / MySQL 8.0.46, eulji_festival, 3306 |
| 런타임 | Spring Boot 3.5.14 / Java 17 / k6 2.3.0 |
| 데이터 | 기존 회원 203명, 전용 테스트 계정 201개 재사용, 재시드 없음 |

기본 조회 5개를 병렬 실행하고 커서 다음 페이지 조회와 좋아요 등록·취소를 이어서 실행했다.
각 VU는 10회 반복마다 본인 프로필을 수정하고 반복 사이 1초 대기했다.
가입·로그인은 준비 단계에서 순차 실행했으며 동시 로그인 성능은 이번 측정 범위에 포함하지 않았다.
준비 단계의 기존 계정 가입 409 응답 201건은 정상 처리했고 본 부하 오류에서 제외했다.
전체 HTTP 요청은 409,336건, 비교에 사용하는 본 부하 요청은 408,933건이다.

## 6. 쿼리 최적화 전후 결과

두 실행 모두 데드락 수정 이후의 동일한 8080·3306 개발 환경이다.
비교 기준 실행은 02:20:23~02:28:38, 이번 실행은 03:19:19~03:27:32 KST다.

| 항목 | 쿼리 최적화 전 | 쿼리 최적화 후 |
| --- | ---: | ---: |
| 최대 동시 사용자 | 200 | 200 |
| 본 부하 요청 | 408,223건 | 408,933건 |
| HTTP 실패 | 0건 | 0건 |
| 응답 계약 검증 실패 | 0건 | 0건 |
| 평균 응답 시간 | 6.38ms | 5.91ms |
| p95 | 21.45ms | 19.025ms |
| p99 | 34.67ms | 33.18ms |

원시 값 기준 평균은 약 7.29%, p95는 약 11.29%, p99는 약 4.32% 낮게 측정됐다.
반면 최대 응답 시간은 약 23.66% 높아졌다. 평균과 백분위 지연의 개선과 순간 최대 지연의 증가는 구분한다.
기존 최초 측정(데드락 수정 전)의 오류 126건과도 달리 이번 실행의 HTTP 오류는 0건이었다.

**DB 연결 대기가 해결됐다고 판단할 수 없다.** 대기가 포착된 샘플 수는 적었지만 대기 최댓값과 최대 지연은 증가했다.
각 실행의 샘플 시점과 JVM·다른 프로세스 상태가 다르므로 최댓값만으로 원인을 단정하지 않는다.
반복 사이 1초 대기가 있는 폐쇄형 부하이며 위 요청률은 서버의 최대 처리 용량을 뜻하지 않는다.

### 데이터 및 로그 검증

- 측정 전·후 `like_count`와 실제 좋아요 행 수의 불일치 모두 0건.
- 본 부하 HTTP 오류와 응답 계약 검증 실패 모두 0건.
- 실행 시간 범위의 앱 로그에서 ERROR·데드락 오류 0건.
- 결과 JSON에 로그인 토큰을 담는 `setup_data`가 없음을 확인.
- 별도 임시 백엔드/DB를 실행하지 않았으며 사용자의 8080 서버는 종료하지 않음.
- 테스트 계정 프로필·방명록 및 좋아요는 시나리오에 따라 변경됨.

## 7. 결과 해석과 측정 범위

이번 실행에서는 오류 없이 평균·p95·p99가 낮아져 SQL 단독 측정의 개선이 API 지연 지표에서도 관측됐다.
그러나 최대 응답 시간, 관측된 연결 대기 및 힙 최댓값은 늘었다. 전체 자원·대기 문제가 해결됐다는 결과는 아니다.

같은 개발 DB와 부하 시나리오를 사용했지만 초기 데이터를 복원하거나 JVM 워밍업·백그라운드 부하를 엄격히 통제한 반복 교차 실험은 아니다.
회원 수는 동일하지만 이전 테스트가 남긴 프로필·좋아요 등은 달라질 수 있다. 따라서 차이를 전부 코드 변경의 순수 효과로 확정하지 않는다.
모든 지연 값은 부하 증가·유지·감소 전체 집계이며 200명 유지 구간만의 백분위 값이 아니다.

다음 분석 후보는 지연 급증 시점의 DB 연결 점유 시간, 트랜잭션과 쿼리 실행 시간, GC/로그 처리의 상관관계다.
이번에 관측된 연결 대기의 직접 원인을 확정한 것은 아니며, 연결 풀 확대나 캐시의 효과도 아직 측정하지 않았다.
