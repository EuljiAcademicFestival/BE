# 이름표 캐시 적용 후 200명 부하테스트

## 5. 최신 검증: 회원별 이름표 캐시 적용

사용자가 재시작한 실제 **8080 서버**에서 Caffeine 이름표 캐시를 확인한 뒤 기존과 같은 200 VU 혼합 부하를 실행했다. 조회 서비스의 읽기 전용 트랜잭션 복원도 함께 반영된 상태다. JWT와 쿼리 최적화·좋아요 데드락 수정은 유지했다.

| 항목 | 조건 |
| --- | --- |
| 날짜 | 2026-11-15 KST |
| 실행 시작 / 준비 완료 / 종료 | 19:07:48 / 19:08:59 / 19:16:00 |
| 앱 / DB | 127.0.0.1:8080 / MySQL 8.0.46, eulji_festival, 3306 |
| 데이터 | 회원 203명, 테스트 계정 201개 재사용, 재시드 없음 |
| 부하 | capacity/mixed, 10→50→100→200 VU, 200명 3분 유지 후 30초 감소 |
| 시나리오 | 조회 6종 + 좋아요 등록·취소 + 10회마다 프로필 수정, 반복 사이 1초 대기 |
| 계측 | JFR 없음, 별도 Actuator 약 1초, Prometheus 약 5초 |
| 캐시 | 회원 ID별 이름·학년, 저장 후 5분, 최대 10,000명, 시작 시 빈 캐시 |

가입·로그인은 순차 준비 단계이며 동시 로그인 부하는 포함하지 않았다. 예상된 중복 가입 409는 본 부하 오류에서 제외했다. 이름표를 제외한 상세·순위·목록·likedByMe·좋아요 수는 캐시하지 않는다.

### DB 연결과 캐시

| 지표 | JWT 기준 | 캐시 적용 |
| --- | ---: | ---: |
| 본 요청당 DB 연결 획득 | 1회 | 0.877회 |
| 약 5초 Prometheus pending 최대 | 42 | 55 |
| 별도 약 1초 pending 최대 | 107 | 55 |
| 1회 대여당 평균 획득 대기 | 1.639ms | 1.476ms |
| 1회 대여당 평균 점유 | 1.332ms | 1.454ms |

본 부하 경계의 앱 요청 카운터 증가는 411,642회, Hikari 획득 증가는 361,138회다. 요청당 1회 기준에서 **12.269%** 감소했다. 이름표 HTTP 요청은 50,809건이고, 전체 요청과 연결 획득의 차이로 추정한 이름표 연결 생략은 50,504회다. 같은 경로에서 예상되는 실제 이름표 DB 조회는 305회이며 서비스 성능 로그의 labels 호출은 305회였다. 두 값의 일치 여부와 수집 경계를 함께 해석한다.

캐시 회원 키 기준 hit 101,310 / miss 308, 적중률 **99.697%**, 종료 시 크기 201명이다. 이것은 HTTP 요청 적중률과 다르다. 한 요청에 두 회원을 읽고 같은 키의 동시 미스는 로딩 전에 묶일 수 있으므로 miss 키 수와 DB 쿼리 수가 같을 필요가 없다. 7분 부하가 5분 TTL보다 길어 만료 후 다시 읽는 비용도 포함한다.

연결 획득 타임아웃 증가 0회, 본 부하 4xx 0건·5xx 0건. 풀의 실제 활성 최대는 10개다. pending은 연결 개수가 아닌 대기 스레드 수다.

## 7. 판단과 측정 한계

**이름표 캐시로 본 요청당 DB 연결 획득이 0.877회로 줄어든 것을 실제 서버에서 확인했다.** 전체 평균·p95·p99도 낮게 관측됐다. 특히 이름표 p95는 약 15.088→4.4ms로 70.8% 낮아졌다. 다른 조회의 p95는 대체로 비슷했고, 커서 다음 페이지·좋아요 등록·취소·프로필 수정 p95는 오히려 높아졌다. 전체 최대 지연도 100.976→120.974ms로 늘었다.

같은 약 5초 Prometheus 표본의 pending 최대는 42→55로 높아졌다. 별도 1초 표본 최대는 107→55로 낮았지만, 순간값만으로 서로 다른 결론을 선택하지 않는다. **연결 획득 횟수 감소는 확인했으나 순간 대기가 해결된 결과는 아니다.** 캐시 키 적중률이 99.7%라도 전체 API의 99.7%에서 DB 연결을 없앤 것은 아니다.

- 조회 트랜잭션 제거는 계속 미채택 상태이고 현재는 복원한 조회 트랜잭션과 캐시를 함께 사용한다.
- 기준 실행과 이번 실행은 시간대·JVM 재시작·워밍업·백그라운드 부하가 달랐다. 초기 데이터도 복원하지 않았다. 지연 차이를 캐시 하나의 순수한 인과 효과로 확정하는 교차 실험은 아니다.
- 이름표가 혼합 반복의 여러 API 중 하나이므로 전체 연결 획득 감소 폭에는 시나리오상 한계가 있다. 한 Mac에서 앱·DB·부하·모니터링을 함께 실행한 결과다.
- 지연은 증가·200명 유지·감소 전체 집계이며 200명 유지 구간만의 p95가 아니다. 관측 pending 최대는 표본 최대이며 대기 시간·실제 연결 수와 다르다.
- 프로필 수정은 같은 이름·학년을 반복 제출하므로 실제 이름 변경에 따른 무효화 부하를 충분히 대표하지 않는다. 커밋·롤백·오래된 로딩 방지는 47개 기능 테스트에서 별도로 검증했다.
- 시작 전·종료 후 좋아요 집계 불일치 모두 0건. 본 부하 시간 범위 ERROR 이벤트 0건, 데드락 관련 로그 0건을 확인했다. 요약 JSON에는 setup_data가 없다.
- 사용자 8080 서버는 종료하지 않았다. 임시 앱·DB나 추가 캐시는 실행하지 않았다.
