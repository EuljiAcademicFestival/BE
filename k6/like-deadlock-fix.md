# 좋아요 데드락 개선

## 원인과 수정

기존 200 VU 혼합 부하에서 좋아요 등록이 126회 HTTP 500으로 실패했다.
방명록 행을 잠근 뒤 좋아요 존재 여부를 `SELECT ... FOR UPDATE`로 확인했는데,
존재하지 않는 좋아요 키를 조회하면 MySQL의 REPEATABLE READ에서 인덱스 갭을 잠근다.
서로 다른 방명록을 수정하는 트랜잭션도 같은 갭을 잠근 채 INSERT를 시도하면 데드락이 발생한다.

빈 좋아요 인덱스에서 두 트랜잭션을 조정하는 회귀 테스트로 기존 코드의 실패를 재현했다.
InnoDB 상태에서 두 트랜잭션 모두 PRIMARY 인덱스의 `supremum` 잠금을 보유하고,
상대의 잠금 때문에 `insert intention waiting` 상태에 놓인 것을 확인했다.

- 방명록별 `FOR UPDATE`는 유지해 좋아요 수 변경을 직렬화한다.
- 좋아요 존재 여부를 미리 잠금 조회하지 않고 INSERT 또는 DELETE를 실행한다.
- INSERT 성공 / DELETE로 실제 삭제된 경우에만 저장된 좋아요 수를 변경한다.
- 중복 키 예외만 이미 좋아요를 누른 상태로 처리한다. 외래 키 위반 등 다른 오류는 전파하고 롤백한다.
- API 경로, 요청·응답 형식, DB 스키마와 트랜잭션 격리 수준은 유지한다.

## 검증

개발 DB와 분리된 MySQL 8.0.46, `eulji_festival_test` DB에서 테스트 28개가 모두 통과했다.
회귀 테스트는 아래를 포함한다.

- 서로 다른 방명록에 대한 빈 인덱스 갭 데드락 재현 조건
- 같은 방명록의 동시 좋아요 등록·취소 및 중복 요청
- 여러 방명록의 좋아요 등록·취소와 프로필 수정 동시 실행
- 기존 REPEATABLE READ 스냅샷이 있는 트랜잭션에서 중복 좋아요 처리
- 존재하지 않는 좋아요 사용자에 대한 외래 키 오류 전파 및 롤백

통합 테스트 실행 시 테스트 DB만 허용한다. 실제 개발 DB URL을 넣지 않는다.

```bash
TEST_DB_URL='jdbc:mysql://127.0.0.1:13307/eulji_festival_test?connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true' \
TEST_DB_USERNAME=root TEST_DB_PASSWORD='' ./gradlew test
```

## 5. 200명 혼합 부하 재검증 조건

이번 결과는 사용자가 IntelliJ에서 실행한 **8080 개발 서버**를 대상으로 측정했다. 이전에 이 페이지에 적었던 임시 서버 18080 측정 결과를 이번 실행으로 교체했다.

| 항목 | 조건 |
| --- | --- |
| 실행 날짜 | 2026-11-15 |
| 실행 시각 | 02:20:23 ~ 02:28:38 KST |
| 계정 준비 완료 | 02:21:36 KST |
| 앱 | Spring Boot 3.5.14 / Java 17, 127.0.0.1:8080 |
| DB | MySQL 8.0.46 / eulji_festival / 127.0.0.1:3306 |
| DB 회원 수 | 203명, 테스트 계정 201개 재사용 |
| 도구 | k6 2.3.0 |
| 동시 사용자 | 최대 200 VU |
| 부하 단계 | 10 → 50 → 100 → 200 VU, 200명 3분 유지 후 30초 감소 |
| 본 시나리오 | 약 7분, 준비 포함 약 494초 |
| 워크로드 | 조회 + 좋아요 등록·취소 + 프로필 수정 |

기본 조회 5개를 병렬 호출한 뒤 커서 다음 페이지 조회와 좋아요 등록·취소를 실행했다. 각 VU는 10회 반복마다 본인 프로필을 수정하고 반복 사이 1초 대기했다.

회원가입·로그인은 준비 단계의 순차 실행이다. 동시 로그인 폭주 성능은 이번 측정 대상에 포함하지 않았다. 기존 계정 가입의 409 응답 201건은 예상된 정상 응답으로 처리했으며 본 부하 오류에서 제외했다. 준비를 포함한 전체 HTTP 요청은 408,626건, 성능 비교에 사용하는 본 부하 요청은 408,223건이다.

8080의 Actuator Prometheus 메트릭을 약 15초 간격으로 별도 수집했다. 아래 수치는 샘플에서 관측된 최댓값이며 순간 최대를 모두 포착한 값은 아니다.

연결 풀을 모두 사용하는 구간과 연결 대기가 관측됐다. 이번 지연 기준은 통과했으므로 연결 풀 크기를 곧바로 늘리기보다는, 추가 최적화 시 쿼리 실행 시간과 트랜잭션의 연결 점유 시간을 확인할 근거로 남긴다.

### DB 및 로그 검증

- 측정 전과 종료 후, 저장된 `like_count`와 실제 좋아요 행 수의 불일치는 모두 **0건**이었다.
- 본 부하 HTTP 5xx 및 4xx 오류는 0건이다. 준비 단계의 예상된 409와 구분했다.
- 실행 시간 범위의 앱 로그에서 ERROR 및 데드락 오류가 발견되지 않았다.
- 결과 JSON에서 로그인 토큰이 포함된 `setup_data`가 제거됐음을 확인했다.
- 이번에는 임시 앱과 임시 MySQL을 실행하지 않았다. 사용자가 실행한 8080 서버는 종료하지 않았다.
- 개발 DB의 테스트 계정 프로필·방명록 및 좋아요가 시나리오에 따라 변경됐다. 데이터 재시드는 실행하지 않았다.

## 7. 결과 해석과 측정 범위

**이번 8080 실행에서는 좋아요 데드락 관련 HTTP 오류가 재발하지 않았고, 좋아요 집계도 정확하게 유지됐다. 응답 시간도 기존 개발 서버 측정값보다 낮게 관측됐다.**

기존과 같은 개발 앱 포트 및 DB 인스턴스를 사용해 임시 환경 차이를 줄였다. 다만 동일한 초기 데이터 복원, JVM 워밍업 조건 통제, 수정 전후 반복 교차 측정까지 수행한 것은 아니다. 따라서 이번 한 번의 측정 차이를 전부 코드 변경의 순수한 속도 개선 효과로 단정하지 않는다.

모든 지연 값은 부하 증가·200명 유지·감소 구간 전체 집계이며 200명 유지 구간만의 p95/p99가 아니다. 한 번의 실행에서 오류가 없었다는 검증이며, 모든 상황의 데드락 가능성을 영구적으로 배제한다는 뜻은 아니다.

이번 요청은 실제 8080 서버의 Actuator 메트릭에 집계된다. 기존 Prometheus가 8080을 정상 수집 중이면 Grafana에서도 이번 실행 시간 범위를 조회할 수 있다. Grafana 화면 자체의 수집 상태를 이번 작업에서 별도로 확인한 것은 아니다.
