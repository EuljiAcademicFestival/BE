## 5. 최신 실험: 단일 조회 트랜잭션 제거

**결론: 이번 후보는 채택하지 않고 코드를 원복했다.** 연결 평균 점유는 줄었지만,
200 VU 두 실행 모두 기존 JWT 구성보다 API 응답이 느렸다.
코드 변경이 원인이라고 확정한 것은 아니지만 API 성능 개선이 입증되지 않아 유지하지 않았다.

### 연결과 서버 내부 지표

같은 약 1초 별도 수집의 본 부하 경계에서 비교했다. timer 합계 차이를 count 차이로 나눈 값이며,
수집 경계와 모든 k6 요청 경계가 완전히 일치하지 않을 수 있다.

| 항목 | JWT 기준 | 제거 1차 | 제거 재측정 |

| 요청당 연결 획득 | 1회 | 1회 | 1회 |

연결 점유는 낮아졌지만 연결 획득 대기 및 HTTP 지연이 개선된 결과는 아니다.
Prometheus의 같은 5초 간격에서도 JWT 기준과 1차의 평균 점유는 약 1.332→1.048ms였고,
평균 획득 대기는 약 1.640→1.730ms, 대기 인원 최대는 42→57로 관측됐다.
재측정의 5초 이력은 이 표에 추가 집계하지 않았다. 서로 다른 간격의 순간 최댓값을 섞지 않는다.

서버 내부 HTTP 평균도 JWT 기준 약 3.325ms에서 1차 약 4.767ms로 늘어,
k6 클라이언트 지연만으로 설명되는 결과는 아니었다. 그러나 연결 외 구간의 증가가 로그·스케줄링 등
어떤 요인 때문인지는 이번 기록만으로 확정하지 않았다. 수정하지 않은 쓰기 API의 지연도 함께 늘었다.

- 두 실행의 HTTP·응답 검증 실패 및 종료 후 좋아요 집계 불일치 모두 0건.
- 각 실행 시간 범위의 ERROR·데드락 로그 0건.

- 성능 실험 동안 임시 백엔드/DB는 실행하지 않았고 개발 서버는 종료하지 않았다.

## 7. 결정과 현재 코드 상태

**조회 서비스의 `@Transactional(readOnly = true)`를 복원했다.**
JWT의 DB 없는 인증, 기존 쿼리 최적화, 좋아요·가입·프로필 등의 쓰기 트랜잭션은 유지한다.
실험 조건을 강제하던 두 회귀 테스트와 스파이는 후보 취소와 함께 제거했다.
실험 당시 기능 테스트 41개는 통과했으며, 원복 후 채택 코드의 전체 테스트 **39개와 bootJar 빌드도 통과**했다.

원복은 소스와 빌드에 완료됐다. 실행 중인 8080 JVM에는 재시작 후 반영되며 원복 후 부하테스트는 아직 하지 않았다.
따라서 원복만으로 현재 환경의 응답 시간이 과거 4.11ms로 되돌아온다고 보장하지 않는다.

이 실험의 부하·회원 수·DB·시나리오는 같지만 초기 데이터를 복원하거나 시스템 부하·JVM 워밍업을
통제한 수정 전후 교차 반복 실험은 아니다. 두 제거 실행이 기준보다 느린 사실과,
그 차이의 원인을 코드 한 변경에 확정하는 주장은 구분한다.
모든 백분위 지연은 증가·유지·감소 전체 집계다.
