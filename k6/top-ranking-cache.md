## 23. REST 상위 순위 1초 공통 캐시 — 구현 및 기능 검증

기록일: <date start="2026-11-16" />

### 목적과 적용 범위

GET /api/rankings/top의 반복 조회가 DB 연결을 매번 획득하지 않도록 1초 공통 캐시를 추가했다. 개인정보 선택 상태 likedByMe가 없는 공통 순위에만 적용한다. 방명록 목록·캐릭터 상세·좋아요 쓰기는 기존 경로를 유지한다.

기존 목록 SQL의 인덱스·커서 분석에서는 현재 203건 데이터에 전체 스캔 문제가 확인되지 않았고, JOIN 전환 후보의 차이는 작아 SQL 변경은 채택하지 않았다. 이번 변경은 공통 조회의 연결 획득 횟수를 줄이는 별도 후보다. 아직 실제 200명 부하의 대기 감소를 입증한 것은 아니다.

### 구조

- 입력 포트 장식자인 CachedGuestbookQueryUseCase가 서비스 트랜잭션 진입 전 캐시를 확인한다.
- TopRankingCachePort와 CaffeineTopRankingCache 출력 어댑터를 추가했다. 공통 키 하나, 최대 한 개 스냅샷이다.
- 만료는 접근 후가 아닌 저장 완료 후 기본 1초다. RANKING_TOP_CACHE_TTL로 조정하며 기본 PT1S이다.
- 동시 캐시 미스·만료 재조회는 한 로더로 합친다. 로더의 기존 읽기 트랜잭션이 끝나 연결을 반환한 뒤 결과가 캐시에 게시된다.
- 빈 순위도 정상 결과로 캐시하고, 로더 실패는 캐시하지 않는다. 결과는 불변 복사본으로 저장한다.
- 동점자는 전원 포함하며 최종 인원을 세 명으로 자르지 않는다. 순위·좋아요 수는 같은 조회 스냅샷에서 함께 저장한다.
- 외부 트랜잭션 안에서는 캐시를 우회한다. 자신의 쓰기를 읽고 미커밋 값을 공통 캐시에 게시하지 않으며, 이미 DB 연결을 잡은 호출자가 캐시 로더를 기다리는 풀 교착 위험을 피한다.
- 좋아요·프로필 수정마다 캐시를 무효화하지 않고 짧은 TTL로 갱신한다. WebSocket 공통 상태 조회는 캐시를 우회하는 기존 별도 SELECT 경로를 유지한다.

### 반영 지연과 프론트엔드 계약

REST의 순위·좋아요 수·프로필·방명록 본문은 TTL 동안 이전 값일 수 있다. TTL은 로딩 완료부터 적용되므로 실제 원본 시점 차이에는 쿼리·전송 지연도 추가된다. WebSocket으로 최신 값을 받은 뒤 늦은 REST 스냅샷으로 덮어쓰지 않아야 한다.

기존 Request/Response 필드·인증·동점 규칙은 유지한다. <mention url="https://app.notion.com/p/00c13f22e202836d9455012c6e365208">상위 순위 REST 명세</mention>에는 프론트엔드가 알아야 할 반영 지연만 반영했다. WebSocket 페이지에는 내부 구현·측정 기록을 추가하지 않았다.

### 검증 결과

개발 DB와 분리된 13307 MySQL의 전용 eulji_festival_test에서 전체 테스트 91개 통과, 실패·오류·건너뜀 0개. bootJar 빌드 성공. 테스트 MySQL은 검증 후 종료했다. 개발 DB 3306은 테스트 정리 대상으로 사용하지 않았다.

- 실제 HTTP 최초 순위 조회: Hikari 연결 획득 1회.
- 캐시 적중 HTTP 조회: Hikari 연결 획득 증가 0회, SQL 어댑터 호출 없음.
- 실제 외부 트랜잭션의 자신의 쓰기 확인과 롤백 후 공통 캐시 오염 방지.
- 가상 ticker로 정확한 1초 만료와 접근으로 TTL이 연장되지 않음 검증.
- 동시 요청 8개의 최초 미스 및 만료 재조회가 각각 로딩 한 번을 공유.
- 공동 1위 다섯 명 전원 보존, 빈 목록 캐시, 불변 복사본, 로딩 실패 후 재시도, 잘못된 TTL 거부.
- 기존 가입·로그인·JWT·좋아요 동시성·순위·커서·이름표 캐시·WebSocket 회귀 검증.

DB 통합 테스트에서는 시간 경과에 따른 우연한 캐시 만료를 피하도록 테스트 TTL을 길게 두고 시나리오 간 스냅샷을 초기화했다. 실제 1초 만료는 가상 ticker 테스트로 따로 검증했다. 순위 SQL 자체의 테스트는 갱신 후 강제 초기화하여 순위 규칙을 검사한다.

### 지표와 실측 상태

```promql
cache_gets_total{cache="topRankings",result="hit"}
cache_gets_total{cache="topRankings",result="miss"}
cache_puts_total{cache="topRankings"}
```

Micrometer 캐시 적중·미스와 Hikari 획득·점유·pending, HTTP API별 p95를 함께 비교한다. 미스 수와 실제 SQL 로딩 횟수는 동시 요청 합치기로 다를 수 있다.

변경 전 200명 REST 혼합 부하를 시도했으나 8080 서버가 꺼져 있어 실행 시작 전 연결 실패했다. 부하 요청은 실행되지 않았으며 이를 기준 측정 결과로 사용하지 않는다. 캐시 적용 후 200명 부하도 아직 실행하지 않았다. 이전 WebSocket 테스트의 낮은 대기와 이번 REST 캐시의 성능을 직접 비교하지 않는다.
