# WebSocket 200명 이동·좋아요 혼합 부하 결과

## 5. 최신 검증: 200명 WebSocket 이동·좋아요 혼합 부하

사용자가 재시작한 실제 8080 서버에 WebSocket과 좋아요 실시간 반영이 적용됐는지 확인했다.
2명·15초 실행을 통과한 뒤 바로 200명을 연결해 각자 약 3분 동안 이동과 좋아요 등록·취소를 함께 수행했다.

| 항목 | 조건 |
| --- | --- |
| 날짜 | 2026-11-15 KST |
| 전체 실행 | 21:49:48~21:54:01 |
| 200명 첫 관측 | 21:51:00 |
| 서버 / DB | 127.0.0.1:8080 / MySQL 8.0.46, eulji_festival, 3306 |
| 데이터 | 회원 203명, 테스트 계정 재사용, 재시드 없음 |
| 도구 | k6/websocket.js, VUS=200, WS_DURATION_SECONDS=180, WS_WITH_LIKES=true |
| 연결 | 200 VU가 각 1개 연결, JWT AUTH 후 3분 유지 |
| 이동 | 회원당 약 초당 10회 MOVE |
| 좋아요 | 회원당 약 1초마다 REST PUT·DELETE를 번갈아 호출 |
| 동기화 | 서버가 커밋된 변경을 기본 200ms 간격으로 합쳐 ENGAGEMENT_STATE 전파 |
| 계측 | JFR 없음, 별도 Actuator 약 1초 / Prometheus 약 5초 |

가입·로그인은 약 72초의 순차 준비 단계다. 기존 계정의 중복 가입 409 응답 200건은 예상된 준비 결과이며 본 부하 오류가 아니다.
별도 임시 앱·DB는 실행하지 않았고 사용자의 8080 서버는 종료하지 않았다.
테스트는 계정 간 좋아요를 변경했다. 3D 렌더링·물리·브라우저 FPS를 측정한 테스트는 아니다.

모든 thresholds가 통과했고 k6 종료 코드는 0이다. 수신 성공률은 각 회원이 해당 프레임을 한 번 이상 받았는지를 검사한다.
모든 변경이 모든 화면에 같은 순간에 적용됐다는 검증은 아니다. 실제 렌더링 프런트엔드 연동은 별도로 확인해야 한다.

### 실시간 반영 지연

| 측정 | 평균 | p95 | 최대 |
| --- | ---: | ---: | ---: |
| 소켓 open→WELCOME | 97.82ms | 215ms | 250ms |
| MOVE 전송→자신의 sequence를 포함한 상태 수신 | 61.536ms | 107ms | 148ms |
| 좋아요 REST 시작→응답 숫자와 일치하는 공통 상태 수신 | 111.333ms | 206ms | 245ms |

좋아요 반영 시간은 숫자 일치가 관측된 요청의 표본이다. 중복 요청·같은 숫자 반복·수신 누락 등은 표본 수와 해석에 영향을 준다.
전체 요청별 순위 반영 완료 시간이나 모든 접속자에게 도달하는 데 걸린 최악 시간을 측정한 값은 아니다.
현재 k6 요약 설정에는 p99가 없으므로 p99를 추정해 적지 않는다.
2명 실행에서는 이동 p95 약 100.8ms, 좋아요 p95 약 198.4ms였다. 두 실행은 규모가 달라 순수 최적화 비교가 아니다.

### DB 연결과 배치 조회

| 항목 | 결과 |
| --- | ---: |
| 전체 실행 Hikari 연결 획득 증가 | 36,839회 |
| 준비 REST에 대응 | 400회 |
| 좋아요 REST에 대응 | 35,848회 |
| 입장 시 프로필 조회에 대응 | 200회 |
| 좋아요·순위 동기화 SELECT | 391회 |
| 위 합계와 실제 연결 획득 차이 | 0회 |
| 동기화 조회 실패 | 0회 |
| 약 1초 / 5초 표본 pending 최대 | 0 / 0 |
| 약 1초 표본 active 최대 / 설정 최대 | 3 / 10 |
| 약 5초 Prometheus 평균 연결 획득 대기 | 0.006ms |
| 약 5초 Prometheus 획득 시간 max | 4ms |
| 연결 획득 타임아웃 증가 | 0 |

연결 획득은 준비 요청 + 좋아요 REST + 입장 프로필 조회 + 동기화 SELECT 합계와 정확히 일치했다.
따라서 약 36만 MOVE에 대해 메시지마다 DB 연결을 빌리지 않는 구조가 실제 실행 지표와도 일치한다.
좋아요 요청 35,848건을 처리하는 동안 실시간 동기화 조회는 391회였다.
중복 요청은 새 변경을 만들지 않을 수 있으므로 이것을 실제 변경 건수나 별도 기존 구현 대비 개선율로 해석하지 않는다.

pending 0은 표본에서의 관측값이다. 수집 사이 순간 대기를 배제하지 않으며, 획득 시간 max가 4ms였으므로
모든 연결을 대기 없이 획득했다는 뜻은 아니다. 시작 직후 200명 프로필 조회의 짧은 active 피크도 1초 표본이 놓칠 수 있다.
점유 시간의 rolling max는 준비 단계 비밀번호 검증의 영향을 남길 수 있어 본 부하의 최고 점유 시간으로 사용하지 않았다.

### 종료 구간의 서버 메시지 거부

서버의 rejected 메시지는 28건이었다. 직전 21:54:00.091 표본까지는 0이고,
21:54:01.109에 접속자·연결이 모두 0으로 내려간 종료 구간에서만 28로 늘었다.
k6 송신 360,056개는 AUTH 200 + 수락 MOVE 359,828 + 거부 28과 일치한다.

현재 핸들러는 연결이 이미 제거돼 acceptMessage가 실패한 경우와 실제 빈도 제한 초과를 같은 거부 카운터로 기록한다.
닫히는 연결에서 늦게 도착한 마지막 MOVE일 가능성과 일치하지만, 사유별 계측이 없어 확정하지 않는다.
정상 유지 중 거부는 표본에서 관측되지 않았고 k6의 조기 종료·클라이언트 오류는 0이었다.
이번 결과를 서버 거부까지 전부 0건이라고 기록하지 않는다. 향후 거부 사유 분리가 필요하다.

### 자원과 전송량

- 앱 사용 힙 표본 최대 약 194.04MiB, 프로세스 CPU gauge 최대 약 20.808%.
- k6 RSS 표본 최대 약 271.156MiB. OS의 k6 CPU 표본 최대 224.4%는 약 2.244개 코어 사용에 해당하며 앱 CPU gauge와 기준이 다르다.
- k6 총 수신량 7.76GB, 총 송신량 약 52.75MB. HTTP·WebSocket 합계다.
- 수신량 대부분이 본 부하에 집중됐다고 보면 약 43.109MB/s, 약 344.873Mbps 규모다.
  정확한 본 부하 네트워크 구간만 분리한 값은 아니며 로컬 루프백 전송이다.
- 위치 프레임 수신량은 회원당 평균 약 8.669회/초다.
  입력은 약 10Hz지만 서버 fixedDelay·처리 비용·프레임 대체·수신 스케줄링이 포함되므로 출력 10Hz를 정확히 보장하는 값은 아니다.

## 7. 판단과 다음 개선

이번 시나리오에서는 200명 연결·이동·좋아요 반영을 클라이언트 오류 없이 처리했고, 좋아요 집계도 일치했다.
실시간 반영 p95는 이동 107ms·좋아요 수 206ms였으며 관측된 DB 연결 대기는 낮았다.
다만 종료 구간 거부 28건과 큰 전송량은 별도 관측 사항으로 남긴다.

**다음 최적화 후보는 위치 상태 전송량이다.** 현재는 움직임이 있으면 전체 접속자의 위치를 모든 접속자에게 보낸다.
변경된 위치만 보내는 delta와 근처 사용자만 받는 관심 영역을 검토할 수 있다. 실제 네트워크가 병목이었다고 확정한 것은 아니다.

과거 200 VU REST 혼합 부하는 조회 6종·좋아요·프로필을 반복했다. 이번에는 연결 유지·이동과 초당 약 1회 좋아요가 중심이다.
HTTP 요청 수·p95·pending을 그 결과와 직접 비교해 동일 부하에서 개선됐다고 주장하지 않는다.
일반 HTTP 지연과 실패 지표에는 준비 로그인·예상 409가 포함되므로 실시간 지연 지표와 분리한다.
한 Mac의 앱·DB·k6·모니터링이 자원을 공유했고 3분·203명 데이터셋으로 운영 환경의 장시간 안정성·최대 수용량을 확정하지 않는다.

실행 구간 ERROR 로그 이벤트 0건, 데드락 관련 로그 0건, 준비를 제외한 HTTP 4xx·5xx는 모두 0건이었다.
최종 WebSocket 연결과 접속자 지표는 모두 0으로 복귀했다. JWT와 비밀번호는 결과에 저장하지 않았으며 setup_data 제거를 확인했다.
