# JWT 전환 후 200명 부하테스트

## 5. JWT 전환 후 200명 혼합 부하 조건

이번 대표 결과는 JWT가 반영된 실제 8080 개발 서버의 실행이다. 이전 DB 토큰 인증 서버의 쿼리 최적화 후 실행과 비교한다.

| 항목 | 조건 |
| --- | --- |
| 실행 일시 | 2026-11-15 04:34:01 ~ 04:42:14 KST |
| 계정 준비 완료 | 04:35:13 KST |
| 앱 / DB | 127.0.0.1:8080 / MySQL 8.0.46, eulji_festival, 3306 |
| 런타임 | Spring Boot 3.5.14 / Java 17 / k6 2.3.0 |
| 데이터 | 회원 203명, 테스트 계정 201개 재사용, 재시드 없음 |
| 인증 | 계정별 신규 JWT를 로그인으로 발급, 서명·만료 로컬 검증 |
| 부하 | capacity / mixed, 최대 200 VU |
| 단계 | 10 → 50 → 100 → 200 VU, 200명 3분 유지, 30초 감소 |
| 길이 | 본 부하 약 7분, 준비 포함 약 492.5초 |
| 계측 | JFR 없음, Actuator 별도 수집 약 1초 / Prometheus 약 5초 |

기본 조회 5개를 병렬 실행하고 커서 다음 페이지와 좋아요 등록·취소를 이어서 실행했다.
각 VU는 10회 반복마다 프로필을 수정하며 반복 사이 1초 대기했다.
회원가입·로그인은 준비 단계에서 순차 실행했다. 동시 로그인 폭주 성능은 측정 대상이 아니다.
기존 계정 가입의 예상된 409 응답 201건은 정상 처리하고 본 부하 오류에서 제외했다.
준비 포함 전체 요청 412,120건, 본 부하 요청 411,717건이다.

## 6. DB 토큰 인증과 JWT 인증 비교

비교 기준은 JFR을 사용하지 않은 쿼리 최적화 후 실행(03:19:19~03:27:32 KST)이다.
JFR 진단 실행(03:45:41~03:53:54)의 p95 22.66ms는 이번 성능 비교의 대표 기준으로 사용하지 않는다.

### DB 연결 비교

| 지표 | JWT 전 | JWT 후 |
| --- | ---: | ---: |
| 본 요청당 연결 획득 | 약 2회 | 1회 |
| 5초 Prometheus에서 관측한 대기 인원 최대 | 72 | 42 |
| 연결 획득 시간 max | 125ms | 99ms |
| 평균 연결 획득 시간: 1회 대여 기준 | 1.609ms | 1.640ms |
| 평균 연결 점유 시간: 1회 대여 기준 | 0.921ms | 1.332ms |
| 연결 획득 타임아웃 증가 | 0 | 0 |

본 부하를 포함한 1초 수집 경계에서 연결 획득 증가는 411,717회로 본 요청 수와 일치했다.
기존 인증·기능의 두 번 대여 구조에서 인증용 대여가 제거된 것을 실제 서버에서도 확인했다.

위 평균 시간은 같은 Prometheus 이력의 timer sum/count 차이로 계산했다.
수집 경계가 k6의 모든 요청 경계와 완전히 같지는 않다.
짧은 인증 대여가 사라져 1회 대여당 점유 시간은 오히려 높아졌지만,
요청당 대여가 2→1회로 줄어 단순 환산한 요청당 연결 점유는 약 1.84→1.33ms다.
요청당 연결 획득 대기도 약 3.22→1.64ms로 환산된다. 이는 요청 지연 전체와 같지 않다.

수집 시점 차이를 구분한다. 과거 별도 15초 수집의 대기 최대는 136, 이번 별도 1초 수집의 최대는 107이었다.
주 비교에는 같은 약 5초 간격의 Prometheus 값 72→42를 사용했다.
어느 수집도 순간 최대를 빠짐없이 보장하지 않으며, 대기 인원은 대기 지속 시간을 의미하지 않는다.
**연결 대기는 줄어든 관측 결과지만 완전히 사라지지는 않았다.**

### 데이터·토큰·로그 확인

- 종료 후 `like_count`와 실제 좋아요 행 수 불일치 0건.
- 본 부하 HTTP 오류·응답 검증 실패 모두 0건, 실행 시간 범위 로그의 ERROR·데드락 오류 0건.
- 사전 로그인에서 새 JWT 발급과 보호된 API의 200을 확인한 뒤 측정했다.
- 테스트 종료 후 별도의 로그인 확인에서도 JWT가 발급됐으며 기존 `access_tokens` 행 수는 807→807로 증가하지 않았다.
- 결과 JSON에는 토큰이 담긴 `setup_data`가 없음을 확인했다.
- 8080 서버는 종료하지 않았고 임시 백엔드·DB도 실행하지 않았다.
- 신규 JWT는 만료까지 유효하며, 회원·기존 토큰 행 삭제가 인증에 즉시 반영되지 않는 정책은 유지된다.

## 7. 결과 해석과 측정 범위

**JWT로 인증의 DB 연결을 제거했고, 이번 실행에서는 평균·p95·p99와 같은 간격에서 관측한 연결 대기 최대가 낮아졌다.**
다만 연결 대기는 남아 있어 모든 순간 대기 문제를 해결한 결과는 아니다.

기존 인증 트랜잭션 제거만의 독립 부하테스트는 수행하지 않았으므로,
이번 수치는 DB 토큰 인증 구현 전체와 JWT 인증 구현 전체의 비교다.
같은 개발 DB·회원 수·부하 시나리오를 사용했지만 초기 데이터를 복원하거나 JVM 워밍업·백그라운드 부하를 통제한 반복 교차 실험은 아니다.
직전 비교 실행의 별도 수집은 15초, 이번은 1초로 계측 비용도 다르다. 5초 Prometheus 기록을 보조 비교에 사용했다.
따라서 관측 차이를 전부 단일 코드 변경의 순수 효과로 확정하지 않는다.

지연 값은 부하 증가·200명 유지·감소 전체 집계이며 200명 유지 구간만의 p95/p99가 아니다.
반복 사이 1초 대기가 있는 폐쇄형 부하로, 요청률은 서버의 최대 처리 용량을 뜻하지 않는다.
