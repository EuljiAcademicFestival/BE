## 11. JWT 인증 전환 — 구현 및 기능 검증

로그인 API와 응답의 `accessToken` 필드는 유지하고, DB 저장 랜덤 토큰을 JWT로 전환했다.
회원가입·비밀번호 검증·기능 API·헥사고날 입력/출력 포트 구조는 유지했다.

### 인증 경로

| 항목 | 기존 | JWT 전환 후 |
| --- | --- | --- |
| 토큰 발급 | 랜덤 토큰 해시를 DB에 INSERT | HS256 서명 JWT 생성 |
| 토큰 확인 | 토큰·만료·회원 존재 SELECT | 서명·알고리즘·클레임 로컬 검증 |
| 인증용 DB 연결 | 요청마다 획득 | 없음 |
| 인증용 트랜잭션 | 앞 단계에서 명시적 트랜잭션 제거 | 없음 |
| 실제 기능의 DB 연결·트랜잭션 | 사용 | 유지 |

JJWT 0.12.7을 사용한다. Gymjjak과 같은 라이브러리이며, 알고리즘 허용 목록 설정의 수정이 포함된 패치 버전을 선택했다.
검증 파서는 한 번 생성해 재사용하고 HS256만 허용한다. 발급자, `token_type=access`,
양의 정수 회원 ID(`sub`), 발급·만료 시각을 검증한다. 만료 시각과 현재 시각이 같은 경계도 거부한다.
개인 프로필이나 비밀번호는 JWT에 넣지 않는다. 발급마다 고유 ID를 넣어 같은 회원의 연속 로그인도 구분한다.

### 설정 및 전환

- `JWT_SECRET`: 최소 32바이트 난수를 Base64로 인코딩한 필수 환경변수.
  기존 로컬 `.env`에 새 난수 키를 생성했고 값은 출력하거나 Git에 올리지 않았다.
- `JWT_ISSUER`: 기본 `eulji-academic-festival`.
- `ACCESS_TOKEN_TTL`: 기존 기본값 1시간 유지, 최소 1초.
- 기존 랜덤 토큰은 전환 후 거부되므로 다시 로그인해야 한다.
- 기존 V1·V2 Flyway 파일과 `access_tokens` 테이블·데이터는 보존한다.
  새 구현은 해당 테이블에 토큰을 저장하거나 인증을 위해 조회하지 않는다.
- Refresh Token, 토큰 갱신·로그아웃 API는 추가하지 않았다.
- 여러 서버는 같은 키와 발급자 설정을 사용해야 한다. 매 실행마다 키를 새로 생성하지 않는다.

### 달라지는 정책

DB 조회 없는 JWT이므로 토큰 행 삭제·회원 삭제로 이미 발급된 JWT가 즉시 폐기되지 않는다.
서명과 클레임이 유효하면 만료 전까지 인증될 수 있으며, 회원 데이터가 필요한 기능은 그 기능의 DB 처리 결과를 따른다.
즉시 폐기가 필요하면 별도 상태 검증이 필요하다. 이번 구현에는 폐기 목록을 추가하지 않았다.

### 검증 결과

분리된 MySQL `eulji_festival_test`에서 전체 **39개 테스트 통과**, 실패·오류·건너뜀 0개. `bootJar` 빌드 성공.

- 정상 발급·서명, 고유 토큰, 만료 전 인증과 정확한 만료 경계의 거부.
- 잘못된 서명·변조·unsigned 토큰·다른 알고리즘·기존 랜덤 토큰·잘못된 형식의 거부.
- 발급자·용도·필수 시각·회원 ID 검증과 미래 발급 시각/사용 시작 시각의 거부.
- 짧거나 잘못된 비밀키와 잘못된 TTL의 시작 단계 오류.
- 실제 인증 필터 경로가 트랜잭션을 열지 않는지 확인.
- JWT 발급 및 유효·무효 토큰 검증 반복 중 Hikari 연결 획득 카운터 증가가 0인지 확인.
- 실제 로그인 응답 및 보호된 API, 401 응답과 JWT의 변경된 폐기 정책 검증.
- 기존 가입·프로필 롤백, 좋아요 동시성·집계, 공동 순위·커서 회귀 테스트 통과.

### 부하테스트 결과

JWT가 반영된 실제 8080 서버에서 200 VU 혼합 부하를 검증했다.
본 요청 411,717건에서 HTTP·응답 검증 실패 및 좋아요 집계 불일치가 모두 0건이었다.
평균 4.11ms, p95 13.072ms로 측정했고 본 부하 DB 연결 획득은 요청당 1회로 확인했다.
연결 대기는 남아 있으므로 완전 해결로 판단하지 않는다.
자세한 조건과 비교 한계는 `k6/jwt-load-test-result.md`를 참고한다.
