## 23. 방명록 목록 SQL 실행 계획 및 EXISTS·JOIN 비교

기록일: <date start="2026-11-16" />

목적: 기존 REST DB 연결 대기의 원인이 목록 SQL의 전체 스캔·잘못된 페이지 조회인지 확인하고, likedByMe를 EXISTS에서 LEFT JOIN으로 바꾸는 후보의 효과를 비교했다. 이번 작업은 SELECT 실행 계획 분석이며 200명 REST 부하를 실행하거나 병목 해결을 검증한 것은 아니다.

### 데이터와 안전한 분석 범위

실제 개발 MySQL 8.0.46, eulji_festival의 방명록 203건을 사용했다. 읽기 전용 트랜잭션에서 SELECT의 EXPLAIN ANALYZE만 실행하고 ROLLBACK했다. DDL·INSERT·UPDATE·DELETE는 실행하지 않았으며 서버·인덱스·애플리케이션 코드를 바꾸지 않았다.

인기순·최신순 각각 첫 페이지, 20번째 항목 이후, 180번째 항목 이후의 6조건을 확인했다. OFFSET은 분석용 커서 값을 고르는 데만 썼고 실제 목록 SQL은 기존 커서 조건을 그대로 사용했다. 페이지 fetchSize는 다음 페이지 존재 여부 확인을 위한 21이다.

### 현재 실행 계획

- 인기순은 idx_guestbook_popular, 최신순은 idx_guestbook_latest를 사용했다.
- 첫 페이지는 커버링 인덱스 스캔, 커서 페이지는 커버링 인덱스 범위 스캔으로 필요한 21건을 읽었다.
- LIMIT으로 페이지를 선택한 뒤 회원·방명록을 PK로 결합했다.
- likedByMe의 EXISTS는 각 페이지 항목에 대해 guestbook_likes 복합 PK로 단건 검색했다. 별도의 JDBC 요청이 21번 발생한 것이 아니다.
- 순위는 기존 최적화대로 상위 점수 3행에서 계산했다. 모든 방명록에 윈도 함수 순위를 계산하지 않았다.
- 실행 계획의 임시 page_entries 스캔·마지막 정렬은 페이지 21건 범위였다. 이 결과만으로 원본 테이블 전체 스캔이라고 해석하지 않는다.

개별 클라이언트 연결로 조건별 12번 측정했을 때 root 실행시간 중앙값은 약 0.382~0.458ms였다. 이는 MySQL 내부 EXPLAIN 계측 시간이며 Hikari 대기·JDBC·JPA 트랜잭션 시작/종료·HTTP 처리 시간은 포함하지 않는다.

### EXISTS를 LEFT JOIN으로 바꾼 후보 비교

후보는 기존 EXISTS 표현을 (viewer_like.liker_member_id IS NOT NULL)로 바꾸고, viewer_like.entry_member_id=e.member_id AND viewer_like.liker_member_id=viewerId 조건으로 LEFT JOIN했다. 복합 PK의 유일성을 사용해 중복 페이지 행이 생기지 않도록 구성했다. 이 후보는 실서비스 코드에 적용하지 않았다.

하나의 읽기 전용 스냅샷·같은 MySQL 클라이언트 연결에서 6조건×2후보를 고정 시드로 무작위 섞어 각 50회, 총 600회 실행했다.

| 정렬·커서 | 기존 EXISTS 중앙값 | JOIN 후보 중앙값 | 기존 p95 | JOIN 후보 p95 |
| --- | --- | --- | --- | --- |
| 인기순 첫 페이지 | 0.04445ms | 0.04225ms | 0.188ms | 0.0793ms |
| 인기순 20번째 이후 | 0.0514ms | 0.0503ms | 0.115ms | 0.108ms |
| 인기순 180번째 이후 | 0.0445ms | 0.0430ms | 0.073ms | 0.0894ms |
| 최신순 첫 페이지 | 0.0425ms | 0.04065ms | 0.0944ms | 0.0568ms |
| 최신순 20번째 이후 | 0.0471ms | 0.0457ms | 0.088ms | 0.121ms |
| 최신순 180번째 이후 | 0.04445ms | 0.0429ms | 0.0962ms | 0.0904ms |

p95는 각 50개 표본을 정렬한 뒤 floor((n−1)×0.95) 위치의 값을 사용했다. 이 표와 앞의 개별 연결 측정은 연결 재사용·워밍업·실행 순서가 달라 수치를 직접 개선율로 비교하지 않는다. 0.4→0.04ms를 쿼리 최적화 성과로 주장하지 않는다.

JOIN 후보의 중앙값 차이는 약 0.0011~0.0022ms였고, 일부 조건의 p95는 더 높았다. 작은 데이터·단일 연결의 측정 잡음과 캐시 효과도 있어 안정적인 개선이나 연결 풀 대기 해결 근거가 되지 않는다. 수백만 행·동시 요청 환경에서의 성능까지 확정하지 않는다.

### 판단과 다음 대상

이번 조건에서는 목록의 무한 스크롤이 전체 스캔을 유발하거나 EXISTS가 별도 DB 요청을 반복하는 구조는 아니었다. 기존 인덱스·LIMIT 선적용·커서 구조는 작동하고 있다. 근거 없는 JOIN 전환이나 인덱스 추가는 하지 않았다. 코드 변경이 없으므로 기능 회귀 테스트를 새로 실행하지 않았다.

이전 JFR의 연결 획득 전 대기와 이번 SQL 내부 실행시간을 구분해야 한다. 빠른 SELECT도 많은 동시 요청이 같은 풀을 사용하면 연결을 기다릴 수 있다. 따라서 기존 병목은 해결됐다고 기록하지 않는다.

다음 개선 후보는 반복되는 공통 조회의 DB 접근 횟수 감소다. 우선 개인 상태가 없는 상위 순위의 짧은 캐시를 검토하고, 변경 전후 동일 200명 REST 혼합 부하에서 연결 획득 횟수·점유 시간·pending·API별 p95를 비교해야 한다. 목록 전체를 개인별 likedByMe·커서·시간 표시까지 그대로 공통 캐시하는 방식은 별도 설계 없이 적용하지 않는다.
