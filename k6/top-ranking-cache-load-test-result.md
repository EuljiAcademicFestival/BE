## 24. 상위 순위 1초 캐시 적용 후 200명 REST 혼합 부하

기록일: <date start="2026-11-16" />

### 실행 조건

사용자가 실행한 실제 8080 서버와 3306 개발 DB에서 01:25:21~01:29:36 KST에 측정했다. 본 부하 첫 관측은 01:26:33 KST다. k6/festival.js의 PROFILE=smoke, VUS=200, SMOKE_DURATION=3m, WORKLOAD=mixed, PAUSE_SECONDS=1로 실행했다. smoke는 constant-vus 분기를 선택하는 이름이며 소규모 테스트가 아니라 200명 고정 부하다.

인기순·최신순·다음 페이지·이름표·캐릭터 상세·상위 순위·좋아요 등록/취소·프로필 수정을 함께 실행했다. 데이터는 회원 203명, 기존 테스트 계정 201개를 재사용했고 재시드하지 않았다. 이름표 캐시와 기본 1초 순위 캐시, 연결 풀 10개, 기존 읽기 트랜잭션·SQL을 유지했다. JFR은 사용하지 않았고 Actuator 약 1초·Prometheus 약 5초로 수집했다. WebSocket 연결 부하는 실행하지 않았다.

사전 순위 API 2회 호출로 캐시 미스·적중을 확인한 뒤 기준 카운터를 잡았으므로, 아래 증분에는 사전 요청을 포함하지 않는다.

### 캐시의 확인된 효과

| 항목 | 결과 |
| --- | --- |
| 상위 순위 HTTP 요청 | 35,072건 |
| 캐시 적중 / 미스 | 34,895 / 177 |
| 캐시 로딩 시도 | 177회 |
| 캐시 적중률 | 약 99.495% |
| 기존 요청마다 조회하는 경로 대비 생략된 순위 조회 | 34,895회, 약 99.495% |
| 본 부하 전체 Hikari 획득 | 214,345회 |

순위 요청 수는 캐시 적중+미스와 정확히 일치한다. 이 어댑터는 로딩에서만 기존 순위 SELECT를 호출하므로, 35,072건의 순위 요청 중 177회만 로딩했다. HTTP·계약 실패가 없었다. 이 수치는 순위 경로의 조회 생략 효과이며 전체 DB 부하나 응답속도가 99.5% 개선됐다는 의미는 아니다.

전체 실행 Hikari 획득은 214,747회이며 준비 가입·로그인 402회를 제외했다. 이름표 캐시 효과도 포함한 값이므로 전체 연결 감소를 순위 캐시에만 귀속하지 않는다.

실제 지표에서 수동 Caffeine 캐시는 cache_load_duration_seconds_count를 노출하지 않는 것을 확인해 23번의 예시를 cache_puts_total로 정정했다. 사용 중인 Micrometer CaffeineCacheMetrics에서 이 값은 stats.loadCount에 대응하며 성공·실패 로딩 시도를 포함한다. 이번 실행에는 HTTP 실패가 없었다.

### 남은 연결 대기

- 약 1초 표본 pending 최대 119, active 최대 10이었다.
- 최대 pending은 01:26:33.859 KST, 본 부하 시작 부근에 관측됐다.
- 본 부하 첫 관측 이후 30초를 제외해도 pending 최대 60이었다. 01:28:44.303 KST에 관측됐으므로 시작 순간만의 현상은 아니다.
- pending이 양수인 표본은 24개다. 표본 수를 대기의 정확한 지속 시간으로 환산하지 않는다.
- 약 5초 Prometheus 표본에서는 pending 최대 8이었다. 1초 수집 최대 119와 수집 간격이 달라 직접 동일시하지 않는다.
- Prometheus 구간 평균 연결 획득 대기는 약 3.145ms, 점유 시간 약 1.560ms, 획득 시간 max는 252ms였다.
- 점유 시간 rolling max 403ms는 준비 로그인 영향을 포함할 수 있어 본 부하의 최고 SQL 실행시간으로 사용하지 않는다.
- 앱 CPU gauge 표본 최대 약 41.13%, 사용 힙 최대 약 252.81MiB. 로컬 공유 환경의 표본이다.
- 종료 후 active·pending은 모두 0으로 복귀했고 사용자 서버는 종료하지 않았다.

### 판단과 다음 확인

순위 캐시가 반복 DB 조회를 줄이는 효과는 확인했다. 하지만 연결 경쟁이 유지 구간에도 남았으므로 기존 REST 병목은 완전히 해결되지 않았다. 최근 WebSocket 부하에서 관측된 낮은 대기와는 다른 시나리오다.

변경 직전의 동일 조건 무캐시 기준 부하는 서버가 꺼져 있어 확보하지 못했다. 따라서 이번 평균·p95·pending을 과거 실행과 비교해 순수 개선율을 산출하지 않는다. 과거 실행은 계측·워밍업·부하 조건이 다를 수 있다. 이번의 조회 생략 수는 코드 경로와 카운터를 바탕으로 한 결과로, 동일 조건 전후 속도 비교와 구분한다.

다음 진단 대상은 목록·상세 등의 연결 획득·점유 구간이다. SQL 내부 시간과 트랜잭션 시작·종료, 로그 출력, 스케줄링을 구분해 확인해야 한다. 이번에는 JFR이나 DB 내부 락 이력을 기록하지 않아 대기 급증의 세부 원인을 확정하지 않는다. 연결 풀 확대나 개인별 목록 캐시는 이번 작업에서 적용하지 않았다.
