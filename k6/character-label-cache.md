## 13. 회원별 캐릭터 이름표 캐시 — 구현·기능 검증

적용 대상은 `GET /api/characters?memberIds=...`의 회원 ID·이름·학년이다.
상세·순위·방명록·좋아요 수·likedByMe는 캐시하지 않는다. 기존 API 형식을 유지한다.

### 구조와 비용

`CachedGuestbookQueryUseCase`가 입력 포트를 장식해 트랜잭션 바깥에서 캐시를 확인한다.
적중하면 기존 조회 서비스에 진입하지 않는다. 미스가 있으면 그 회원들만 모아 기존 읽기 트랜잭션과
IN 쿼리 한 번에 위임한다. ID 조합 전체가 아니라 회원별로 저장해 서로 다른 화면에서도 재사용한다.
정렬·중복 제거·누락 회원 생략 규칙을 유지한다. 존재하지 않는 ID와 실패한 로딩 결과는 저장하지 않는다.

기존 조회 트랜잭션 제거 실험은 원복 상태를 유지한다.
다른 조회는 기존 서비스로 그대로 위임하고 쓰기 트랜잭션도 유지한다.

### 무효화와 경합

- 이름 또는 학년이 실제로 바뀐 경우에만 커밋 후 해당 회원을 무효화한다.
- 캐릭터 ID·방명록만 변경되거나 이름·학년이 같으면 불필요하게 비우지 않는다.
- 롤백되면 기존 캐시를 유지한다. 외부 트랜잭션 안에서는 캐시를 우회해 자신의 쓰기를 읽고 미커밋 값은 캐시하지 않는다.
- 동일 키의 동시 미스는 고정 개수의 로딩 잠금으로 묶고 여러 미스는 일괄 조회한다.
- 커밋 무효화와 진행 중인 이전 값 로딩이 겹치면 세대 번호를 확인해 오래된 값이 재저장되지 않게 한다.
- 무효화는 SQL 로더의 잠금을 기다리지 않는다. 커밋 콜백이 아직 DB 연결을 잡은 동안
  DB 연결을 기다리는 로더와 서로 기다리지 않도록 로딩 잠금과 게시 잠금을 분리했다.
- 부가 동시성 상태도 고정 크기로 두어 임의의 회원 ID 요청에 따라 무한히 커지지 않는다.

### 설정과 지표

Caffeine 로컬 캐시이며 기본 저장 후 TTL은 5분, 최대 10,000명이다.
`CHARACTER_LABEL_CACHE_TTL`, `CHARACTER_LABEL_CACHE_MAXIMUM_SIZE`로 조정한다.
애플리케이션 한 대 안에서 무효화된다. 다중 서버·DB 직접 변경은 별도 무효화 설계 없이는 TTL까지 이전 값이 남을 수 있다.

Prometheus 지표:

```promql
cache_gets_total{cache="characterLabels", result="hit"}
cache_gets_total{cache="characterLabels", result="miss"}
cache_size{cache="characterLabels"}
```

적중률은 조회한 회원 키 단위이며 HTTP 요청 적중률과 구분한다.
실제 감소량은 캐시 적중·미스와 Hikari 연결 획득 횟수를 함께 비교한다.

### 검증 결과

분리된 실제 MySQL 테스트 DB에서 전체 **47개 테스트 통과**, 실패·오류·건너뜀 0개, bootJar 빌드 성공.

- 실제 HTTP의 캐시 적중에서 Hikari 연결 획득 증가 0.
- 여러 미스 회원을 요청해도 연결 획득 1회 및 미스 ID만 일괄 조회.
- ID 정렬·중복 제거와 응답 형식 보존.
- 프로필 커밋 전 다른 요청에는 기존 이름표, 커밋 후 새 이름·학년 반영.
- 미커밋 데이터 조회는 캐시 우회, 롤백 후 기존 캐시 유지.
- 이름·학년이 같고 다른 필드만 바뀌면 무효화하지 않음.
- 만료, 누락 회원의 추후 등장, 로딩 실패 후 재시도, 동시 미스 및 오래된 로딩의 재저장 방지.
- 기존 JWT·좋아요 동시성·롤백·공동 순위·커서 테스트 통과.

### 부하 검증 상태

기능과 DB 연결 생략은 검증했다. IntelliJ Gradle 동기화와 8080 서버 재시작 후 같은 200 VU 테스트로
캐시 적중률·전체 DB 연결 획득·API 지연을 비교해야 한다. 현재 단계에서 성능 개선이나 대기 해결을 확정하지 않는다.
