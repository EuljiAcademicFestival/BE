## 27. 조회 서비스 readOnly 해제 후 200명 비교 측정

기록일: <date start="2026-11-16" />

### 조건

사용자가 최신 코드를 실행한 8080 서버에서 02:18:13~02:22:28 KST에 실행했다. 본 부하 첫 관측은 02:19:25 KST다. 24번과 동일한 k6/festival.js, PROFILE=smoke, VUS=200, SMOKE_DURATION=3m, WORKLOAD=mixed, PAUSE_SECONDS=1 조건이며 JFR 없이 측정했다. 25번 JFR 진단 실행을 속도 비교 기준으로 삼지 않았다.

조회 서비스는 @Transactional을 유지하고 readOnly만 해제했다. SQL·캐시 TTL·풀 크기 10·쓰기 서비스는 동일하다. 순위 캐시 사전 미스·적중 확인 후 기준 카운터를 잡았다. 기존 회원 203명과 테스트 계정 201개를 재사용했으며 재시드하지 않았다.

### 유지 구간의 연결 점유·획득 대기

준비와 시작 부근 영향이 큰 rolling max를 평균과 혼동하지 않도록, 두 실행 모두 본 부하 첫 표본 이후 30초가 지난 첫 표본부터 종료까지 카운터 증분으로 다시 계산했다.

| 항목 | 24번 유지 구간 | 이번 유지 구간 |
| --- | --- | --- |
| 구간 시작 KST | 01:27:04.522 | 02:19:56.447 |
| 구간 종료 KST | 01:29:36.912 | 02:22:28.963 |
| 획득 카운터 증가 | 177,579 | 177,628 |
| 평균 연결 점유 | 1.567ms | 1.461ms |
| 평균 연결 획득 대기 | 3.140ms | 3.048ms |
| pending 최대 | 60 | 58 |

유지 구간 평균 점유는 약 6.8% 낮게 관측됐고 획득 대기는 약 2.9% 낮았다. 이는 한 번씩의 실행에서 관측된 차이이며 보편적인 개선율이나 readOnly 해제의 순수 인과 효과로 확정하지 않는다. 구간 경계는 약 1초 표본이고 각 실행의 시점은 다르다.

이번 전체 pending 최대 150은 02:19:25.811 KST, 본 부하 시작 부근에서 관측됐다. 시작 30초를 제외해도 최대 58이므로 반복적인 연결 경쟁은 남아 있다. 종료 후 active·pending은 모두 0이며 사용자 8080 서버는 종료하지 않았다.

### Prometheus 표본 비교 시 주의

약 5초 Prometheus 표본 pending 최대는 24번 8, 이번 150이다. 두 실행에서 짧은 급증을 포착하는 시점이 달랐고, 1초 수집 최댓값은 각각 119·150이었다. 평균이나 최댓값 하나만으로 대기 문제가 개선됐다고 판단하지 않는다.

Prometheus 구간 평균 점유는 1.560→1.459ms, 획득 대기는 3.145→3.019ms였다. 이는 위의 30초 제외 카운터 구간과 범위가 다르므로 같은 평균으로 취급하지 않는다. 이번 획득 시간 rolling max는 229ms였고 점유 max 404ms에는 준비 로그인 영향이 남을 수 있다.

### 판단

readOnly 해제 후 기능·정합성 문제는 없었고 연결 점유 평균은 조금 낮게 관측됐다. 하지만 전체 평균 응답은 거의 같고 p95도 소폭 차이인 반면 p99와 초기 pending 최대는 증가했다. 따라서 주요 HTTP 성능 개선이나 DB 연결 병목 해결을 입증했다고 결론 내리지 않는다.

현재 코드는 사용자 요청대로 readOnly 해제 상태를 유지했다. 전체 트랜잭션 제거·풀 확대·추가 캐시·SQL 변경은 하지 않았다. 동일 조건 반복 확인이나 남은 대기 구간 분석 없이 이번 한 쌍의 수치만으로 채택·원복 효과를 확정하지 않는다. 이번에는 JFR을 켜지 않아 실제로 어떤 JDBC 왕복이 줄었는지는 직접 추적하지 않았다.
