# 캐시 적용 후 연결 경합 위치 진단

## 결론

연결 획득 대기는 주로 **방명록 목록·상위 순위·캐릭터 상세의 조회 트랜잭션 시작**에서 발생했다.
별도로 **동기 콘솔 출력과 Logback 출력 잠금**도 요청 스레드를 지연시키는 것을 확인했다.
연결을 점유한 상태에서는 SELECT뿐 아니라 읽기 전용 설정, 커밋, 연결 상태 복원에도 DB 통신이 있었다.

이번 기록은 경합 위치를 확인한 진단 결과다. 특정 SQL 하나가 모든 pending 급증을 유발했다거나,
모든 연결 대기의 원인이 로그라고 확정한 결과는 아니다. 아직 코드를 수정하지 않았다.

## 기존 캐시 부하의 로그 확인

이전 19:07:48~19:16:00 KST 캐시 부하에서 최대 pending 55가 포착된
19:11:40 전후의 HTTP·서비스 로그를 traceId로 연결했다.

- 방명록 목록 요청 한 건은 HTTP 59ms, 서비스 내부 기록은 0ms였다.
- 상위 순위 47ms, 상세 40ms 등 여러 조회가 함께 지연됐다.
- 서비스 로그는 트랜잭션 시작 전 연결 획득, 종료·로그 출력 등의 전체 시간을 보장하지 않는다.
- 이것만으로 SQL 실행이 59ms 걸렸다거나 특정 API가 원인이라고 결론 내리지 않았다.

원본: `k6/results/label-cache-peak-request-correlation.json`.

가입·로그인은 순차 준비 단계이고 JFR 분석은 본 부하 19:24:00~19:27:02로 제한했다.
이름표 캐시에는 이전 실행의 항목이 있었지만 시간이 지나 만료돼 초기 재로딩이 발생했다.

단계 증가 대신 처음부터 200명을 사용했고, JVM은 이미 워밍업됐으며 JFR 1ms 계측 비용도 추가됐다.
따라서 이전 캐시 성능 측정과 평균·p95·pending 최대를 직접 비교해 개선·악화를 판단하지 않는다.

## 1. 연결을 기다린 위치

대표 호출 경로:

```text
GuestbookQueryService 프록시의 page / topRankings / detail
  → TransactionInterceptor
  → JpaTransactionManager.doBegin
  → HikariDataSource.getConnection
  → HikariPool.getConnection
  → ConcurrentBag.borrow
  → SynchronousQueue / LockSupport.park
```

본 부하 구간에서 선별된 연결 풀 ThreadPark는 129,626개, 대기 합계는 약 907.902 스레드·초다.

| 처리 | park 이벤트 | 여러 스레드의 대기 합계 | 선별된 풀 대기 합계 비중 |
| --- | ---: | ---: | ---: |
| 방명록 목록 page | 58,954 | 420.945초 | 46.36% |
| 상위 순위 topRankings | 21,916 | 160.581초 | 17.69% |
| 캐릭터 상세 detail | 21,716 | 160.328초 | 17.66% |
| 좋아요 등록·취소 | 25,464 | 151.409초 | 16.68% |
| 프로필 등 회원 명령 | 1,403 | 9.627초 | 1.06% |
| 이름표 캐시 미스 조회 | 173 | 5.012초 | 0.55% |

목록 page는 인기순·최신순·커서 조회 3종이 공유한다. 호출 수 자체가 다른 API보다 많으므로
46.36%만 보고 인기순 SQL 하나가 가장 느리다고 해석하지 않는다.
조회 3개 경로가 이 선별 대기 합계의 약 81.7%였다. 인증의 DB 연결 대기는 관측되지 않았다.

이 비중은 전체 HTTP 지연 비중이 아니다. 병렬 스레드 대기를 합친 값이라 실행 시간보다 클 수 있다.
한 연결 획득 중 여러 번 park할 수 있어 이벤트 수는 요청 수·연결 획득 횟수와 다르다.
1ms 미만 park는 제외됐고 요청이 없어 쉬는 Tomcat 작업 스레드는 집계에서 제외했다.

### pending 124의 순간

19:24:03.161에는 active 10, pending 124, Tomcat busy 139가 표본에 기록됐다.
해당 시각과 겹치는 JFR 풀 대기 이벤트는 목록 49, 상세 24, 좋아요 23, 순위 22개였다.
따라서 여러 기능의 요청이 함께 제한된 풀을 기다린 것을 확인했다.
JFR 임계치와 Hikari 표본 시점이 달라 118과 124가 같을 필요는 없다.

19:24:14.273에도 별도 표본 pending 56이 있었고 JFR에서 목록·순위·상세의 풀 대기를 다시 확인했다.
시작 시점 하나에서만 관측된 현상은 아니지만, 표본만으로 대기의 지속 시간을 확정하지 않는다.

## 2. 연결을 점유하는 동안의 처리

1ms 이상 JDBC 소켓 읽기는 다음 구간에 분포했다.

| 구간 | 이벤트 | 여러 스레드의 소켓 읽기 시간 합계 | 단일 최대 |
| --- | ---: | ---: | ---: |
| 트랜잭션 시작 | 2,551 | 5.266초 | 45.246ms |
| SELECT 등 쿼리 처리 | 3,719 | 6.691초 | 47.789ms |
| 커밋 | 2,262 | 4.801초 | 100.050ms |
| 트랜잭션 종료 후 정리 | 713 | 1.372초 | 27.518ms |

조회 시작에서는 `ConnectionImpl.setReadOnlyInternal` → MySQL 통신 경로가 잡혔다.
커밋에서는 `ConnectionImpl.commit`, 정리에서는 `setAutoCommit`을 통한 DB 통신도 확인했다.
즉, 연결 점유를 SQL 실행 시간 하나로만 설명할 수 없었다.

이 표는 임계치 이상 소켓 이벤트의 합계다. 전체 쿼리 시간·전체 연결 점유 시간이나 각 구간의
정확한 비중을 계산한 표가 아니다. 모든 대여·반납을 요청별로 짝지은 것도 아니다.
DB 내부의 실행·락 대기와 네트워크·JVM 스케줄링 시간까지 분리한 것은 아니다.
과거 조회 트랜잭션 제거 실험을 그대로 다시 적용해야 한다는 근거로 사용하지 않는다.

## 3. 별도로 확인된 동기 로그 경합

19:24:29.021~19:24:29.173, 좋아요 처리 스레드의 콘솔 쓰기 한 번이 **151.333ms** 걸렸다.

```text
GuestbookCommandService.setLike 프록시
  → TransactionInterceptor.invokeWithinTransaction
  → PerformanceLogAspect.measureExecutionTime
  → Logger.info
  → OutputStreamAppender.writeBytes
  → ConsoleTarget / PrintStream / FileOutputStream.write
```

이 호출 순서에서는 성능 로그 출력이 트랜잭션 안에 있다.
로그 출력이 끝나야 서비스 프록시에서 커밋·연결 반환을 계속할 수 있으므로,
로그 쓰기 지연이 해당 요청의 연결 점유를 연장하는 경로가 확인된 것이다.

같은 19:24:29.100 시각에 다음 JFR 이벤트가 겹쳤다.

- 인증 서비스 성능 로그의 출력 잠금 대기: 107개 스레드.
- 목록 조회 성능 로그의 출력 잠금 대기: 2개 스레드.
- 기타 HTTP 로그 출력 잠금 대기: 2개 스레드.
- 위 151ms 콘솔 쓰기 진행 중: 좋아요 스레드 1개.

전체 선별된 로그 ThreadPark는 4,132개·약 45.090 스레드·초였고,
그중 인증 서비스 로그 경로가 약 38.573 스레드·초였다.
JWT 검증이 DB를 조회해서 기다린 것이 아니라 **인증 메서드마다 남기는 성능 로그**에서 기다렸다.
모니터 잠금 이벤트도 1개·1.319ms 있었다.

현재 `PerformanceLogAspect`는 모든 public application service 메서드에 INFO 로그를 남긴다.
`!prod` 설정은 해당 로그를 동기 CONSOLE과 PERFORMANCE_FILE에 출력한다.
따라서 이 실행에서는 다음 두 병목이 별도로 확인됐다.

1. 여러 기능이 DB 연결 풀을 기다리는 경합.
2. 요청 스레드가 같은 동기 로그 출력 잠금을 기다리는 경합.

151ms 콘솔 쓰기는 pending 124가 기록된 19:24:03과 다른 시점이다.
19:24:29.100에는 분석 대상에서 동시 풀 park가 잡히지 않았으므로,
이 로그 사건 하나로 모든 DB pending 피크를 설명하지 않는다.
콘솔 소비자가 왜 그 쓰기를 늦췄는지까지 확정한 것은 아니다.

## 4. 캐시 잠금과 GC

- 이름표 캐시 로딩 잠금: 1ms 이상 park 69개, 합계 약 4.015 스레드·초, 최대 210.640ms.
- 캐시가 만료된 상태로 200명이 함께 접근한 초기 로딩에서 키별 로더를 기다리는 경로가 확인됐다.
- 캐시의 DB 조회 대기는 전체 선별 풀 대기의 0.55%였다. 지속적인 주요 풀 대기 경로는 다른 조회였다.
- GC pause 최대는 JFR에서 약 4.488ms였다. 151ms 로그 쓰기를 긴 단일 GC 정지로 설명할 근거는 없다.
- 임계치 아래 사건, 짧은 GC와 OS 스케줄링의 기여까지 배제한 것은 아니다.

## 다음 개선 우선순위

확인된 동기 콘솔 경합부터 분리하는 것이 다음 실험 후보다.
부하 측정 시 성능 로그의 콘솔 출력을 제외하고 파일 로그는 보존하거나,
매 요청 인증 성능 로그의 양을 줄이는 변경을 각각 분리해 비교할 수 있다.
이번 작업에서는 로그 설정·트랜잭션·SQL·풀 크기를 변경하지 않았다.

이후 같은 200명 고정 조건에서 풀 대기와 API 지연을 다시 확인한다.
연결 풀 증설이나 조회 트랜잭션 제거는 DB 왕복·점유 비용과 실제 HTTP 지연을 함께 검증해야 한다.
