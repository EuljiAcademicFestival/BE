### 사유와 시점으로 확인한 내용

- 00:40:24.815 KST: 접속자·연결 200, 본 부하 거부 증가 0.

- 00:40:26.118 KST: 접속자·연결 모두 0, 증가량은 32건으로 유지.

정상 유지 구간이 아니라 테스트 사용자의 연결 종료 구간에서 발생했다. k6 송신 360,058개는 AUTH 200 + 수락 MOVE 359,826 + 거부 32와 정확히 일치한다. 연결 입력 빈도 초과 RATE_LIMIT은 이번 실행에서 없었다.

19번에서 제시한 “이미 제거된 transport 채널” 경로가 이번 실측의 사유는 아니었다. 이번에 관측한 것은 공간 서비스의 AUTH_REQUIRED 경로다. 핸들러에서 이미 인증된 MOVE로 분기한 뒤 공간의 synchronized move 메서드에 진입했을 때, players에 해당 캐릭터가 없으면 requirePlayer가 AUTH_REQUIRED를 던진다. 실제 k6 MOVE 형식은 인증 전 분기로 들어가면 필드 검사에서 INVALID_MESSAGE가 되므로 이번 AUTH_REQUIRED와 구분된다.

즉, 마지막 MOVE가 인증 확인을 통과한 후 공간 처리를 기다리는 사이 퇴장 처리가 먼저 완료되어, 이동할 캐릭터가 이미 제거된 상태가 된 경합 경로와 일치한다. 이것은 새 로그인에 실패한 32명이 있다는 의미가 아니며 32는 메시지 수다.

### 제어된 순서 재현

PresenceRejectionReasonTest에 실제 FestivalPresenceService를 사용하는 테스트를 추가했다.

1. 정상 입장한 캐릭터의 마지막 MOVE가 transport 인증 확인을 통과하게 한다.
2. 공간 잠금을 잡아 MOVE가 공간 처리에 진입하는 시점을 늦춘다.
3. 같은 잠금 안에서 퇴장을 먼저 처리해 캐릭터를 제거한다.
4. 잠금을 풀면 MOVE가 진입하면서 AUTH_REQUIRED 1건이 기록되고 RATE_LIMIT과 CONNECTION_CLOSED는 0이다.

재현 테스트 클래스의 5개 테스트가 모두 통과했다. 이번 추가 작업은 재현 테스트·기록이며 실제 종료 처리 동작은 추가로 변경하지 않았다. 기존 관련 26개 회귀 테스트와 빌드 통과는 19번의 계측 수정 단계 기록이다.

이번 32건의 사유·종료 시점과 코드 경로를 확인했지만 각 메시지의 스택·정확한 잠금 대기 시간, 퇴장 트리거가 정상 close 콜백·tick·송신 실패 중 무엇이었는지는 건별로 기록하지 않았다. 과거의 28건·26건은 사유 계측 전이므로 같은 원인이라고 소급 확정하지 않는다.

### 판단과 다음 선택

이번 실행에서 확인한 문제는 정상 이용 중 메시지 폭주가 아니라 퇴장과 마지막 MOVE 처리의 경합이다. 종료된 사용자의 위치를 더 반영할 대상이 없어 거부된 것이며 클라이언트 오류·집계 불일치는 없었다. 이것을 메시지 손실 0이나 모든 종류의 장애 0으로 확대 해석하지 않는다.

개선 후보는 정상적으로 퇴장한 연결의 늦은 MOVE를 인증 오류와 구분해 처리·계측하는 것이다. 인증 전 MOVE 차단·실제 빈도 제한·비정상적인 공간 상태 오류를 숨기지 않도록 별도 종료 상태와 규칙을 검토해야 한다. 이 후보는 아직 적용하지 않았다. 프론트엔드 계약 변경은 없어 WebSocket 명세에는 측정 내용을 추가하지 않는다.
