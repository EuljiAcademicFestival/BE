## 10. JFR을 추가한 200명 진단 부하테스트

실행일: 2026-11-15. 앞의 쿼리 최적화 성능 비교와 달리, 이번 실행은 연결 대기 위치를 확인하기 위한 진단 실행이다.
8080 개발 서버와 3306 개발 DB를 그대로 사용했고 캐시·연결 풀·비즈니스 코드는 변경하지 않았다.
부하 시나리오는 기존과 같은 capacity/mixed, 200 VU 3분 유지다.

### 기록 방법과 범위

- 실행: 03:45:41~03:53:54 KST, 계정 준비 완료 03:46:53.
- Hikari 획득·점유 시간, GC, 활성·대기 연결을 약 1초 간격으로 수집했다.
- 실행 중인 JVM에 JFR을 연결했다. 재시작이나 별도 백엔드 서버 실행은 하지 않았다.
- 안전한 설정으로 전환한 JFR 파일은 03:47:24부터 기록했다.
  200명 유지 구간은 포함하지만 본 부하 초반 약 31초는 이 파일에 포함하지 않는다.
- ThreadPark/모니터 경합은 5ms 이상, 소켓·파일 입출력은 2ms 이상을 기록했다.
- 환경변수·시스템 속성·JVM 실행 인자 이벤트는 제외했다. JFR과 파생 원본은 로컬 Git 제외 폴더에 보관한다.
- 프로파일링과 더 잦은 메트릭 수집의 비용이 추가됐으므로 이전 실행과 엄격한 속도 비교를 하지 않는다.
- 종료 후 이번 JFR만 중지했다. 8080 서버는 계속 실행 중이다.

### 호출 경로로 확인된 대기 위치

03:50:15.180 KST에 활성 연결 10개, 대기 인원 144개가 관측됐다.
동일 시각의 JFR에서 다음 경로로 멈춘 요청 스레드 117개를 확인했다.

```text
JpaTransactionManager.doBegin
  → HikariDataSource.getConnection
  → HikariPool.getConnection
  → ConcurrentBag.borrow
  → SynchronousQueue.poll / LockSupport.parkNanos
```

이는 **SQL 실행을 위한 연결을 얻기 전, 트랜잭션 시작 단계에서 연결 풀을 기다리는 상황**을 직접 보여준다.
144개와 117개는 서로 다른 계측의 순간값이고 JFR에는 임계치보다 짧은 park 등이 빠지므로 정확히 같을 필요는 없다.
같은 구간의 03:50:15.174에 발생한 GC 정지는 약 1.15ms였고, 최대 대기가 관측된 시각 전에 종료됐다.
이번 급증을 긴 GC 정지만으로 설명할 근거는 없다. 짧은 GC나 스케줄링의 기여까지 배제한 것은 아니다.

### JFR에서 선별된 연결 풀 대기

| 호출 경로 | 5ms 이상 park 이벤트 수 | 여러 스레드의 대기 시간 합계 |
| --- | ---: | ---: |
| 인증 트랜잭션 시작 | 62,646 | 490.07초 |
| 방명록·캐릭터·순위 조회 트랜잭션 시작 | 48,213 | 373.81초 |
| 좋아요 처리 | 2,315 | 16.86초 |
| 회원 명령 처리 | 88 | 0.59초 |

전체 선별된 풀 대기 park는 113,262개, 합계 약 881.32 스레드·초다.
병렬 스레드의 합계이므로 테스트 경과 시간과 다르다. 인증 경로가 이 합계의 약 55.6%였다.
이 비율은 전체 HTTP 지연에서 인증이 차지하는 비율이나 모든 연결 획득의 비율을 의미하지 않는다.
하나의 연결 획득 안에서 여러 번 park할 수 있으므로 이벤트 수를 요청 수로 해석하지 않는다.

본 부하 연결 획득 카운터는 815,040회 증가했으며 요청 407,520건의 정확히 2배였다.
코드의 인증 트랜잭션과 기능 트랜잭션이 따로 연결을 빌리는 구조와 일치한다.

### 다른 대기와의 구분

- 2ms 이상 JDBC 소켓 대기는 SQL 조회뿐 아니라 트랜잭션 시작·커밋·정리 경로에도 기록됐다.
  기록된 단일 소켓 읽기 최댓값은 약 19.08ms였다. 이는 전체 SQL/트랜잭션 시간이 아니다.
- 로그 관련 5ms 이상 잠금 대기 68개와 2ms 이상 파일 쓰기 93개도 기록됐다.
  기록된 로그 잠금 대기 최댓값은 약 10.47ms다. 로그 비용이 0이라는 의미는 아니다.
- 요청이 없어 작업 큐에서 쉬는 Tomcat 스레드 park는 `idle_worker`로 분리했다.
  이것을 DB 대기나 병목으로 합산하지 않았다.
- JFR 기록에 데이터 손실 이벤트는 없었다. 다만 임계치 이하 이벤트와 안전한 기록 전환 이전 구간은 분석에서 빠진다.

### 판단 및 다음 개선 후보

이번 실행에서는 **제한된 10개 연결을 여러 요청이 경쟁하고, 인증과 기능의 별도 트랜잭션 시작에서 대기하는 경로**를 확인했다.
캐릭터 상세 SQL 하나의 지연이나 긴 GC 정지만을 원인으로 지목할 근거는 없다.
서버 내부 DB 잠금의 정확한 사건 이력, 모든 요청의 연결 획득/반납 쌍과 전체 트랜잭션 시간까지 기록한 것은 아니다.
과거 실행에서 순간 최댓값이 달라진 직접 원인도 이번 기록만으로 소급 확정하지 않는다.

다음 후보는 **단일 SELECT인 인증 조회에 별도 JPA 트랜잭션이 필요한지 검토하는 것**이다.
인증의 만료·탈퇴 회원·동시성 동작을 보존하면서 트랜잭션 설정·종료 비용을 줄일 수 있는지 검증해야 한다.
인증 쿼리 자체도 연결이 필요하므로 트랜잭션을 없앤다고 연결 획득 횟수가 자동으로 1회가 되는 것은 아니다.
이 변경이나 캐시·연결 풀 확대는 이번 진단 작업에서는 적용하지 않았다.
